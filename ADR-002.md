# ADR-002 — Arquitectura de Suscripciones, Plan Base y Facturación de Actividades

**Estado:** Aprobado

**Fecha:** Julio 2026

---

# Contexto

El sistema nació pensado para administrar únicamente membresías de gimnasio.

Posteriormente se agregaron actividades como:

- Yoga
- Rehabilitación
- Pilates
- CrossFit
- etc.

Esto generó la necesidad de definir cómo convivirán las actividades con las membresías sin romper la arquitectura existente.

Los objetivos principales son:

- mantener una única suscripción por socio;
- evitar duplicar lógica de renovación;
- permitir que un socio haga únicamente actividades;
- permitir combinar gimnasio + actividades;
- mantener el sistema simple y escalable.

---

# Problema

Un socio puede encontrarse en cualquiera de estas situaciones:

- solamente gimnasio;
- gimnasio + una o varias actividades;
- solamente actividades.

La pregunta era:

> ¿Las actividades deben crear otra Subscription?

La respuesta es **NO**.

El sistema seguirá teniendo exactamente una Subscription por socio y período.

---

# Decisión

La Subscription seguirá siendo la entidad principal de facturación.

Cada Subscription tendrá:

- exactamente un MembershipPlan principal;
- cero o más SubscriptionItems.

---

# Arquitectura

```
Member

↓

Subscription

    plan (MembershipPlan)

↓

SubscriptionItems

    Yoga
    Rehabilitación
    Pilates
    ...
```

---

# Plan principal

El MembershipPlan representa únicamente la membresía principal del gimnasio.

Ejemplos:

- Básico
- Medio
- Premium
- Gold
- Base Plan (interno)

Nunca existirán dos planes principales activos en la misma Subscription.

---

# SubscriptionItems

SubscriptionItem representa exclusivamente servicios adicionales.

Ejemplos:

- Yoga
- Rehabilitación
- Nutrición
- Personal Trainer
- CrossFit
- Pilates

Los SubscriptionItems nunca representan la membresía del gimnasio.

---

# Base Plan

Se introduce un MembershipPlan especial denominado **Base Plan**.

Este plan:

- es un MembershipPlan normal;
- pertenece al gimnasio;
- está oculto para usuarios y staff;
- solamente existe para mantener consistente la arquitectura.

El socio nunca lo selecciona manualmente.

---

# Objetivo del Base Plan

Permitir que exista una Subscription válida cuando un socio consume únicamente actividades.

Ejemplo:

```
Subscription

Plan:
    Base Plan

Items:
    Yoga
```

Esto evita:

- Subscription sin plan;
- múltiples Subscription por socio;
- lógica especial para actividades.

---

# Visibilidad

El Base Plan nunca aparece en:

- listado de planes;
- alta de socios;
- cambio de plan;
- portal del socio;
- dashboard;
- formularios de administración.

Únicamente podrá configurarse desde la configuración del gimnasio.

---

# Precio del Base Plan

Cada gimnasio puede configurar el precio del Base Plan.

Ejemplos:

```
Base Plan = $0
```

Permite actividades sin pagar acceso base.

o

```
Base Plan = $10.000
```

El gimnasio cobra un acceso mínimo para realizar actividades sin contratar gimnasio.

Esto permite distintos modelos de negocio sin modificar la arquitectura.

---

# Configuración del gimnasio

Se agrega una configuración:

```
Permitir actividades sin membresía
```

```
allow_activity_without_membership = True / False
```

Si está deshabilitado:

- ningún socio podrá permanecer únicamente con Base Plan.

Si está habilitado:

- el sistema permitirá socios únicamente con actividades.

---

# Regla de renovación

El algoritmo de renovación mantiene exactamente lo que el socio posee.

Ejemplos

## Gimnasio solamente

```
Premium
```

↓

```
Premium
```

---

## Gimnasio + Yoga

```
Premium

Yoga
```

↓

```
Premium

Yoga
```

---

## Base + Yoga

```
Base

Yoga
```

↓

```
Base

Yoga
```

---

## Base sin actividades

```
Base
```

↓

No se renueva.

La Subscription expira automáticamente.

---

# Cambios de plan

Los cambios de plan afectan únicamente al MembershipPlan principal.

Ejemplo

Antes

```
Premium

Yoga
```

Después

```
Gold

Yoga
```

Las actividades permanecen intactas.

---

# Agregar actividades

Agregar una actividad únicamente crea un SubscriptionItem.

Ejemplo

Antes

```
Premium
```

Después

```
Premium

Yoga
```

No se crea una nueva Subscription.

---

# Eliminar actividades

Eliminar una actividad únicamente cancela el SubscriptionItem correspondiente.

Ejemplo

Antes

```
Premium

Yoga

Rehabilitación
```

Después

```
Premium

Rehabilitación
```

---

# Pasar de Gimnasio a Actividades

Si un socio desea dejar la membresía de gimnasio pero continuar con actividades:

Antes

```
Premium

Yoga
```

Después de la renovación

```
Base

Yoga
```

---

# Pasar de Actividades a Gimnasio

Si un socio posee únicamente actividades:

Antes

```
Base

Yoga
```

Y decide contratar gimnasio:

Después

```
Premium

Yoga
```

No se crea otra Subscription.

Simplemente cambia el MembershipPlan principal.

---

# Cancelación total

Si el socio cancela toda relación con el gimnasio:

Antes

```
Premium
```

o

```
Base

Yoga
```

Después

No existe renovación.

La Subscription expira.

---

# Cálculo del total

El total de la Subscription siempre será:

```
Subscription.plan.price

+

SUM(SubscriptionItems activos)
```

Ejemplos

```
Premium = 40.000

Yoga = 12.000

Rehabilitación = 30.000

Total = 82.000
```

---

```
Base = 0

Yoga = 12.000

Total = 12.000
```

---

```
Base = 10.000

Yoga = 12.000

Total = 22.000
```

---

# Beneficios

Esta arquitectura permite:

- una única Subscription por socio;
- una única lógica de renovación;
- un único flujo de pagos;
- un único flujo de cambio de plan;
- actividades independientes;
- escalabilidad para futuros servicios.

En el futuro podrán agregarse nuevos SubscriptionItems como:

- Locker
- Toalla
- Nutrición
- Personal Trainer
- Estacionamiento
- Evaluación física
- Otros servicios

sin modificar la arquitectura principal.

---

# Principios de diseño

El sistema mantiene las siguientes reglas:

- Un socio posee una única Subscription activa por período.
- Toda Subscription posee exactamente un MembershipPlan principal.
- Las actividades son servicios adicionales representados mediante SubscriptionItems.
- El Base Plan es un detalle interno de implementación y nunca un producto visible para el usuario.
- La Subscription representa el período de facturación.
- Los SubscriptionItems representan los conceptos facturables adicionales.
- El total siempre surge del plan principal más la suma de los SubscriptionItems activos.

---

# Conclusión

Se adopta definitivamente una arquitectura basada en:

- **1 socio**
- **1 Subscription**
- **1 MembershipPlan principal**
- **N SubscriptionItems**

Este modelo mantiene la simplicidad del sistema original, evita duplicar lógica, facilita el mantenimiento y permite extender el SaaS con nuevos servicios sin necesidad de rediseñar el núcleo de suscripciones.
